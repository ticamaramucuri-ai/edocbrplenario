# Etapa 045 — versão observável nos serviços

**Data:** 04/11/2026. **Estado:** incremento local concluído; verificação fora do host pendente.

O app expõe `GET /api/v1/health`; realtime, webhooks, scheduler (SQLite e PostgreSQL) e worker de correio incluem `version` em `/health`. O valor vem de `EDOCBR_BUILD_VERSION`. A stack de homologação passa `STAGE_BUILD_VERSION` ao build da imagem compartilhada; na ausência do valor, `local-unversioned` explicita que a revisão implantada não pode ser identificada. A sonda `staging-remote-check.py` registra a versão do app e das sondas diretas, além das sondas indiretas retornadas por `platform/system-status`.

**Correção de proveniência local:** a stack antes passava `STAGE_BUILD_VERSION` como variável de runtime em cada serviço. Isso permitia trocar a versão anunciada sem trocar a imagem. O Dockerfile agora incorpora o identificador no build, expõe `EDOCBR_BUILD_VERSION` a todos os processos da mesma imagem e grava `org.opencontainers.image.revision`. O Compose não define build próprio. A sonda continua comparando app e workers com `--expected-version`; alterar o `.env` após construir a imagem não muda o valor observado. `scripts/staging-build.py` exige o SHA completo de um commit Git disponível e constrói a imagem de um `git archive` desse commit, sem absorver arquivos modificados ou não rastreados do diretório. `stack-up` usa esse roteiro. Isso comprova a origem dos arquivos de projeto do build local; não substitui assinatura do artefato nem homologação em host separado.

**Verificação local:** `python3 -I tests/test-staging-remote-check.py`, `bun run lint`, `bun run typecheck` e `GET /api/v1/health` na aplicação local. O teste cobre a versão simulada em app/realtime/webhooks, falha de serviço e relógio divergente. A leitura local retornou `local-unversioned`, como esperado sem variável de deploy.

**Próximo gate:** implantar a imagem identificada em host separado e executar a sonda a partir de observador externo com `--expected-version` igual à revisão implantada. Divergência em qualquer serviço esperado reprova a sonda. Repetir após uma atualização. O ensaio local não fecha a fase 045.

**Prova local de 05/11/2026:** após o commit `077995e271a9d0e2e08d2b23d4e719ac2a16d2e0`, com checkout versionado limpo, defini esse SHA no `.env` privado e reconstruí a imagem compartilhada. O rótulo `org.opencontainers.image.revision` coincidiu com o SHA. App, realtime, webhooks, scheduler e mail worker foram recriados a partir dela; a stack ficou saudável e a sonda pelo gateway local retornou **0**, com cinco versões iguais ao SHA. Com `--expected-version` deliberadamente diferente, retornou **1** e apontou divergência nos cinco serviços. Os `package-lock.json` não versionados dos dois mini-serviços são excluídos do contexto Docker; não entraram na imagem. Esta prova vincula a versão observada ao argumento e rótulo do build local, mas não substitui a assinatura/atestado de artefato CI nem o observador em outro host.

**Prova local de 06/11/2026:** no commit `560c14201ef70a41bdc10c947958c756599fbd8d`, o roteiro exportou a árvore Git com `git archive` para um contexto temporário de 7,51 MB e compilou a imagem de produção. O Compose deixou de oferecer um caminho alternativo de build. A validação com o SHA anterior foi recusada antes do build; com o SHA de `HEAD`, `--check` passou. A imagem recebeu rótulo igual a `560c142...`, e app, realtime, webhooks, scheduler e mail worker foram recriados a partir do mesmo ID de imagem e ficaram `healthy`. A sonda no gateway local retornou **0**, `ok: true`, `remoto: false`, cinco serviços com o mesmo SHA e nenhum inacessível. Com versão esperada `000000...`, retornou **1** e cinco divergências. `python3 -m py_compile` passou para os roteiros alterados, `docker compose config --quiet` e `git diff --check` passaram; o build Next.js incluiu compilação TypeScript. A prova é local e não fecha a homologação da fase 045.

**Ajuste operacional:** a primeira versão do roteiro exigia `HEAD`, por isso recusou um SHA anterior. Agora aceita qualquer commit Git existente indicado por SHA completo, permitindo reconstruir a revisão testada após commits de documentação. Um SHA inexistente é recusado antes do Docker. A versão ainda deve ser conferida na imagem e nos serviços após a implantação.
