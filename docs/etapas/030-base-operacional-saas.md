# Etapa 030 — Base operacional PostgreSQL

**Data:** 11/10/2026 · **Estado:** em andamento. Prova isolada de esquema, restauração e cálculo de saúde em PostgreSQL concluída; migração da aplicação pendente.

`bun run test:postgres:foundation` cria uma instância efêmera de PostgreSQL 16 com porta aleatória restrita ao loopback, deriva o esquema PostgreSQL do Prisma atual, valida o modelo, aplica o DDL, insere um tenant fictício, gera `pg_dump`, restaura em outro banco e confirma 70 tabelas e o tenant restaurado. Gera também um cliente Prisma PostgreSQL temporário e executa a coleta de saúde em duas Câmaras, com recorte de 30 dias e isolamento. Por fim, gera o cliente da aplicação para PostgreSQL, executa a jornada legislativa da etapa 029 (39 verificações) e restaura o cliente SQLite na saída, inclusive em caso de falha. Execute o ensaio sem o servidor local em uso, pois a geração troca temporariamente o cliente Prisma em `node_modules`. A CI executa a prova em um job próprio. O contêiner e os artefatos temporários são removidos ao sair. Isso não migra dados reais nem altera o banco SQLite do piloto.

O cálculo de saúde na aplicação deixou de usar `strftime`, comparação de epoch e `$queryRawUnsafe`: usa contagens Prisma por tenant com `Date`. `bun run test:tenant:health-portability` comprova no SQLite que os contadores novos coincidem com o SQL ainda usado pelo scheduler; o ensaio PostgreSQL comprova a mesma rotina da aplicação no outro provedor.

**Bloqueios para ativação:** o cliente Prisma principal ainda é gerado para SQLite por padrão; `mini-services/realtime`, `scheduler` e `webhooks` usam `bun:sqlite`; o SQL do scheduler para saúde continua específico de SQLite. O caminho absoluto obsoleto do serviço de webhooks foi removido: `WEBHOOKS_DB_PATH` pode apontar para o banco do piloto, com padrão relativo ao projeto. Os scripts de migração e a maioria dos testes integrados também pressupõem SQLite. A jornada 029 demonstrou apenas um caminho crítico da aplicação em PostgreSQL. Portanto, ainda não se pode apontar `DATABASE_URL` da implantação completa para PostgreSQL. A migração exigirá adaptar esses consumidores, gerar migrações versionadas, testar a aplicação inteira com Postgres, ensaiar cópia de dados com preservação de IDs/hashes e definir reversão, RTO/RPO e hospedagem com a operação.

**Próxima entrega:** refatorar acesso a eventos/contadores dos mini-serviços, separar SQL por provedor, executar a jornada 029 em PostgreSQL e ensaiar reversão de uma migração aditiva. Até lá, SQLite permanece como banco do piloto. Segredos ficam em variáveis de ambiente/arquivos privados; o ensaio usa apenas credencial descartável em contêiner acessível pelo loopback local.
