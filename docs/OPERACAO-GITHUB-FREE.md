# Desenvolvimento no GitHub Free

**Estado em 09/11/2026.** O repositório `e-docBR/edocBRplenario` é privado. O GitHub Free para organizações inclui franquia mensal de Actions para runners padrão hospedados; após o consumo, execução sem método de pagamento válido pode ser bloqueada. Os jobs do PR #41 foram recusados com aviso de cobrança ou limite, antes de iniciar. Não há runner próprio registrado no repositório. A página de cobrança da organização não ficou acessível pela conta CLI usada no ensaio; o saldo exato e a causa específica exigem conferência por administrador em **Settings → Billing & licensing**.

## Operação sem minutos pagos

1. Manter o repositório privado. Torná-lo público para obter Actions ilimitadas exporia o código e exige decisão separada de licença, segredos, histórico e propriedade intelectual.
2. Executar a CI hospedada **uma vez por PR** e uma vez após merge em `main`. A regra `push` não dispara mais CI em toda branch; `concurrency` cancela superseded runs do mesmo ref. Isso reduz consumo futuro, mas não remove o bloqueio já existente.
3. Executar o observador externo hospedado a cada **hora**, em vez de a cada 15 minutos. São até 720 execuções mensais, contra até 2.880; cada job pode ser arredondado para um minuto faturável. O atraso potencial de detecção sobe para cerca de 60 minutos. Para alerta mais rápido sem minutos hospedados, implantar observador externo independente com mecanismo próprio e responsável operacional; nunca usar a mesma VPS como única sonda de sua disponibilidade.
4. Rodar testes locais descartáveis antes de publicar PR. Registrar comando, resultado e SHA no arquivo de etapa. Teste local **não substitui** a CI remota quando o gate de promoção a exige.
5. Para continuidade sem franquia hospedada, provisionar **runner próprio em máquina/VM dedicada e isolada** da VPS de aplicação, com runner vinculado ao repositório privado e sem segredos de produção. Usar imagem efêmera ou limpeza integral após cada job; restringir PRs de fork, egress e permissões do token. O executor atual precisa de Docker para PostgreSQL, FFmpeg e Chromium; dimensionar o host antes de transferir os jobs. Runners próprios não consomem minutos hospedados, mas hardware e administração têm custo próprio.
6. Após ativar runner próprio, alterar `runs-on` dos jobs de CI para rótulo exclusivo e comprovar os três jobs em commit idêntico. **Não** apontar CI de PR para a VPS de produção; código de PR executado no host de produção poderia alcançar dados e chaves. A anotação atual menciona cobrança **ou** limite e não comprova que um runner próprio possa iniciar jobs antes da regularização da conta; fazer um job sem segredos para confirmar. Enquanto não há runner próprio comprovado ou franquia restabelecida, manter PR aberto e não promover à VPS.
